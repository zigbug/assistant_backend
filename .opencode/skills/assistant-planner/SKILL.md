# Ассистент-планировщик (assistant-vps)

Персональный трекер задач, событий и планов дня. Живёт на удалённом MCP-сервере
`assistant-vps`; все его tools доступны с префиксом `assistant-vps_`.

| Tools | Префикс вызова |
| --- | --- |
| `list_tasks`, `create_task`, `update_task`, `delete_task` | `assistant-vps_` |
| `get_today_plan`, `generate_plan`, `get_plan_stats`, `update_plan_item` | `assistant-vps_` |
| `list_events`, `create_event`, `update_event`, `delete_event` | `assistant-vps_` |
| `get_current_time` | `assistant-vps_` |

## Три сущности — не путай

- **Задача** — то, что нужно *сделать*. Имеет статус, важность, срочность, дедлайн.
- **Событие** — то, что *занимает время*. Имеет начало и окончание. Статуса нет, выполнить нельзя.
- **План дня** — сгенерированная сетка на дату: события на своих местах + задачи + просроченное.

Пользователь говорит «поставь встречу» / «напомни мне» / «запиши дедлайн» — определи,
задача это или событие. Встреча с конкретным временем → событие. «Надо сделать до пятницы» → задача.

## Железные правила

1. **Всегда начинай с `get_current_time`.** Не выдумывай сегодняшнюю дату.
   Сервер отдаёт UTC, локальное время, часовой пояс и смещение.
   Относительные «сегодня», «завтра», «в пятницу» считай от этого ответа.

2. **Формат дат.** Даты-время — ISO 8601 с `Z`, т.е. UTC:
   `2026-10-05T10:00:00Z`. Только дата — `YYYY-MM-DD` (`scheduled_date`, `repeat_end_date`).
   Всё хранится в UTC, локальное смещение бэкенд не применяет.

3. **Аргументы tools — в snake_case** (`starts_at`, `event_id`, `importance`).
   Во внутренний HTTP-запрос MCP сам конвертирует в camelCase. Модель camelCase не пишет.

4. **`ends_at` обязателен для события с временем.** Без него бэкенд вернёт ошибку, и
   длительность события неизвестна. Для события на целый день — `is_all_day: true`, `ends_at` не нужен.

5. **Короткое внутри большого — `can_overlap: true`.** Звонок, запись к врачу, заказ
   на маркетплейсе внутри рабочего блока: иначе система считает это конфликтом.

6. **`generate_plan` стирает прогресс.** Он **удаляет все элементы плана и создаёт заново**
   из событий, запланированных задач и просроченных. Все прежние отметки `done`/`skipped`
   и заметки будут потеряны. Не вызывай его повторно просто чтобы «освежить» план,
   если пользователь уже отмечал выполненное.

7. **Удаление необратимо.** `delete_task` / `delete_event` — спрашивай подтверждение,
   если не следовало из явного намерения пользователя.

8. **Повторения.** У задач `recurrence` создаёт шаблон, из которого экземпляры
   материализуются на 30 дней вперёд. У событий `recurrence` + `by_weekdays` — **только
   метаданные**: бэкенд не разворачивает повторения в отдельные записи, и в плане дня
   появится только базовая дата. Не обещай пользователю «каждый вторник будет создаваться».

## Статусы

**Задача:** `todo` · `in_progress` · `waiting` · `done` · `cancelled` · `backlog`

**Элемент плана:** `planned` · `inProgress` · `done` · `skipped` · `moved` · `cancelled`

Обрати внимание: у задач статусы в `snake_case`, у элементов плана — в `camelCase`.
Это не опечатка в инструменте.

**Значимость и срочность** — целые от 1 до 5. По умолчанию 2. Ставь 4–5 только если
пользователь прямо обозначил срочность; иначе 2–3.

## Рецепты

### «Что у меня сегодня?»
1. `get_current_time`
2. `get_today_plan`
3. Если план пуст или устарел — `generate_plan` с датой, **но спроси**, если в нём
   уже были отметки о выполнении (см. правило 6).

### «Запланируй мой день»
1. `list_events` c `filter: today` — что уже занимает время.
2. `list_tasks` — что нужно сделать.
3. Уточни оценки (`estimated_minutes`), если их нет: без них задача попадёт в план
   без длительности.
4. Создай недостающее, затем `generate_plan`.
5. `get_plan_stats` — доля выполнения.

### «Каждое утро с 10 до 12 рабочий блок»
`create_event`:
```json
{
  "title": "Рабочий блок",
  "starts_at": "2026-10-05T10:00:00Z",
  "ends_at": "2026-10-05T12:00:00Z",
  "recurrence": "daily",
  "by_weekdays": ["mon", "tue", "wed", "thu", "fri"]
}
```
Дни недели: `mon`…`sun`. Ограничить буднями — перечисли пять.
Одиночная встреча — тот же вызов без `recurrence` и `by_weekdays`.

### «Перенеси созвон на час позже»
`list_events` → найти ID → `update_event` с новыми `starts_at` и `ends_at`.
Сдвигай **оба** конца, иначе событие растянется или станет отрицательным.

### «Сделал задачу»
`update_task` с `status: "done"`. Если задача была в серии — не трогай шаблон,
закрой только экземпляр.

### «Что горит?»
`list_tasks` c `overdue: true`, затем `list_tasks` c `status: "in_progress"`.

## Известные баги (проверено на живом сервере)

Бэкенд отдаёт план вложенным — `{plan: {...}, items: [...], stats: {...}}` — а три tools
читают поля верхнего уровня. Поэтому:

- `generate_plan` печатает `ID плана: null`, `Дата: null`, `Элементов в плане: 0`,
  хотя план создан.
- `get_today_plan` показывает пустые дата и список элементов.
- `get_plan_stats` без `plan_id` возвращает «План на сегодня не найден».

**Что делать:** не сдавай пользователю `null` как правду. Если видишь эти null — сообщи,
что вызовы планов сейчас не работают корректно, и предложи проверить через `list_tasks`
/ `list_events`. Не выдумывай содержимое плана.

`list_tasks`, `list_events` и все операции записи работают корректно.

## Разбор ошибок

Tools возвращают `isError: true` и текст, а не бросают исключение. Частые:

| Сообщение | Причина и что делать |
| --- | --- |
| `Не указан ends_at` | Добавь `ends_at` или `is_all_day: true`. |
| `days parameter must be between 1 and 365` | `list_events` c `days` > 365. |
| `Event with id=N not found` | Событие удалено или ID выдуман. Вызови `list_events`, возьми реальный ID. |
| `ClientException ... connection refused` | Бэкенд недоступен. Не выдумывай данные — сообщи пользователю. |
| `Не указаны поля для обновления` | В `update_*` не передан ни один изменяемый параметр. |

## Правило честности

Если tool вернул ошибку — не выдумывай ID, даты или «уже создал». Скажи, что не получилось,
и покажи, что именно упало. Пользователь полагается на эти данные для своей жизни.
